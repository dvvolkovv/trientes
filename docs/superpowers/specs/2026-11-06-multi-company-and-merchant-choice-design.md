# Несколько компаний у пользователя и выбор компании при заявке приёма (Слайс G1)

**Дата:** 2026-11-06
**Раздел:** кабинет физлица `/{locale}/cabinet#companies`; карточка компании
`/{locale}/cabinet/companies/[id]`; секция приёма на карточке монеты

## Контекст

Слайс F1 поставил на карточку монеты кнопку «Я принимаю эту монету». На живом
прогоне владелец нажал её, завёл точку — и точка оформилась от имени компании
POOLWATT, которую он не выбирал. Кнопка брала первое найденное членство
(`findFirst` в `getMerchantCta`) и уводила в него без вопроса.

Вторая причина того же: **второй компании у пользователя быть не может.** На
таблице `Company` в базе до сих стоит уникальный индекс `Company_ownerUserId_key`.
В `schema.prisma` `@unique` с `ownerUserId` уже снят — но правку в базу
сознательно не вносили (задокументированный дрейф, см. комментарий в
`20261106190000_coin_card/migration.sql`). Поэтому форма «добавить компанию» в
кабинете рисуется всегда, а вторая компания падает на P2002, который
`createCompany` даже не ловит.

## Принципы

1. **Система не выбирает за человека, от чьего имени он действует.** Если
   компаний больше нуля, кнопка спрашивает, а не угадывает.
2. **Права считаются по членству.** `CompanyMember` — единственный гейт;
   `Company.ownerUserId` остаётся для модерации, аудита и уведомлений.
3. **Снятое ограничение заменяется лимитом, а не ничем.** Уникальный индекс
   держал спам случайно; вместо него — явные пределы.
4. **Путь не теряет контекст.** Человек пришёл с карточки монеты — куда бы его
   ни завела регистрация новой компании, монета остаётся отмеченной.
5. **Молчаливого ожидания не бывает.** Если точка не появится на карте, пока
   модератор не одобрит компанию, это написано в форме, а не выясняется неделю.

## Что меняется

### 1. Одна компания на аккаунт → сколько угодно

Миграция снимает `Company_ownerUserId_key`, оставляя обычный индекс
`Company_ownerUserId_idx`. Схема уже соответствует этому состоянию — миграция
закрывает дрейф для `Company` и ничего больше не трогает.

`FintechCompany.ownerUserId @unique` **не трогается**: финтех-каталог — другая
сущность с другим смыслом владения, и его ограничение в этом слайсе не
обсуждалось.

### 2. Лимиты вместо уникального индекса

В `createCompany`:

- `MAX_COMPANIES_PER_USER = 10` — всего компаний, где пользователь состоит
  как OWNER. Код ошибки `too_many_companies`.
- `MAX_PENDING_COMPANIES_PER_USER = 3` — одновременно в статусе `PENDING`.
  Код ошибки `too_many_pending_companies`.

Считается по `CompanyMember` с ролью OWNER, а не по `ownerUserId`: человек,
которого сделали владельцем чужой компании, тоже расходует лимит.

### 3. Кнопка «Я принимаю эту монету» спрашивает, от чьего имени

`getMerchantCta` перестаёт возвращать одну компанию. Новая форма ответа:

```ts
type MerchantCta =
  | { kind: "login" }
  | { kind: "register_company" }                       // компаний нет совсем
  | { kind: "choose"; companies: MerchantCompany[]; acceptedTotal: number }

type MerchantCompany = {
  id: string;
  displayName: string;
  status: RequestStatus;      // PENDING-компания показывается с пометкой
  acceptedPoints: number;     // точек этой компании, уже принимающих карточку
};
```

На карточке это рисуется списком: «Добавить точку в <компания>» для каждой, плюс
отдельная ссылка «…или оформить новую компанию». В списке не больше
`MERCHANT_COMPANY_LIMIT = 5` компаний; если их больше, последняя строка ведёт в
`/cabinet#companies`. Компании со статусом `PENDING` остаются в списке с пометкой
статуса — скрывать их значит прятать от человека его же компанию.

**Починка заодно:** строка «вы принимаете в N точках» считалась по одной
компании. Теперь `acceptedTotal` — сумма по всем компаниям пользователя.

### 4. Регистрация компании по пути не теряет монету

`CreateCompanyForm` получает необязательный проп `nextCard`. При успехе
редирект идёт на `/cabinet/companies/<new>?card=<cardId>#add-point` вместо
`/cabinet/companies/<new>`. Ссылка «оформить новую компанию» с карточки монеты
ведёт на `/cabinet?card=<cardId>#companies`, страница кабинета прокидывает
`card` в форму.

Непонятный `card` молча игнорируется — как и в префилле формы точки (F1).

### 5. Предупреждение о модерации компании

`fetchApprovedPointsInBbox` и `getAcceptanceSummary` требуют
`company.status = APPROVED`. Значит точка компании, которая сама ещё на
модерации, не видна нигде. В форме точки (`PointForm`) над кнопкой отправки
появляется строка, когда статус компании не `APPROVED`:
«Компания ещё на модерации — точка не появится на карте и в счётчике, пока
компанию не одобрят». Текст — ключ `business.pointHiddenUntilCompanyApproved`.

## Границы слайса

**Входит:** снятие уникального индекса, лимиты, выбор компании в кнопке,
перенос карточки через регистрацию компании, предупреждение о модерации,
починка счётчика по всем компаниям.

**Не входит (отдельный слайс G2, решения ещё не приняты):** удаление компаний и
точек приёма, в том числе мультиподпись для удаления сотрудником. Открытые
вопросы по G2 перечислены ниже — без ответов на них проектировать нельзя.

## Открытые вопросы по удалению (слайс G2)

1. **Кто удаляет без голосования.** Рабочее чтение: владелец компании (OWNER)
   удаляет сам; член с ролью EDITOR не может удалить вообще, только запросить, и
   запрос подтверждают владельцы; админ сайта удаляет из админки всегда и с
   записью в `AdminAuditLog`. Требует подтверждения.
2. **Мягко или жёстко.** Рекомендация — мягко, одним механизмом `deletedAt` и
   для компании, и для точки: каскадное физическое удаление уносит историю
   модерации и оставляет висячие `targetId` в `AdminAuditLog`.
3. **Форма мультиподписи.** Для карточек монет есть `CoinCardPolicy` +
   `CoinCardRevision` + `CoinCardApproval` и чистая арифметика в
   `coin-card-multisig.ts`. Для компаний такого нет. Нужна новая модель запроса
   на удаление с голосами владельцев (порог = все OWNER кроме заявителя, при
   одном владельце это вырождается в «владелец подтвердил»).

## Ошибки и валидация

`too_many_companies`, `too_many_pending_companies` — новые коды `createCompany`.
Остальные пути кодов не меняют.

## Тестирование

Чистыми функциями, без базы:
- лимиты компаний: девять существующих пропускают десятую, десять отбивают;
  три PENDING отбивают четвёртую, одобренные в этот лимит не входят;
- выбор компании: ноль компаний → `register_company`; одна → `choose` с одной
  строкой; шесть → в списке пять и признак «есть ещё»;
- `acceptedTotal` суммируется по компаниям, а не берётся из первой;
- ссылка после регистрации компании несёт `?card=` и фрагмент `#add-point`
  именно в этом порядке.

Интеграционно: вторая компания у того же владельца создаётся без P2002.
