# Второй фактор входа для сотрудников — замысел

2026-11-18. Слайс BA. Продолжение линии комплайнса: спека прав сотрудников
(`2026-11-17-compliance-staff-roles-design.md`) назвала второй фактор следующим
слайсом и объяснила, почему его не взяли туда: «второго фактора в проекте нет ни
у кого вообще — это отдельный слайс, а не приписка».

## Зачем

Сегодня человек с правом `APPROVE` на очереди бирж может залистовать биржу,
человек с `APPROVE` на KYB — пустить предприятие на витрину, владелец — выдать
права кому угодно. Всё это защищено **одним паролем**, который можно подобрать,
подсмотреть или выманить письмом. Ограничитель входа (10 неудач с адреса,
5 на пару «адрес + имя») бьёт по подбору, но не по украденному паролю: вор
набирает верный пароль с первого раза.

Второй фактор — минимум, который требуют и SOC 2, и ISO 27001 для
привилегированного доступа, и он же единственная защита от «пароль утёк».

## Решения

1. **TOTP, а не код на почту и не SMS.** Код на почту переносит защиту на
   почтовый ящик — а именно через ящик идёт и сброс пароля, то есть второй
   фактор совпал бы с первым путём восстановления. SMS ломается подменой
   SIM-карты и требует платного шлюза, которого у нас нет. TOTP (RFC 6238)
   работает любым приложением, которое у человека уже есть, и ничего не стоит.
2. **Пароль — не предмет второго фактора, предмет — сеанс.** Фактор
   проверяется **после** создания сеанса, а не внутри входа по паролю:
   у нас четыре провайдера входа (пароль, Google, GitHub, Telegram), и
   встраивать проверку в каждый — четыре места, где можно забыть. Вместо этого
   у строки `Session` появляется штамп `mfaAt`, а вход в `/admin` требует
   штампа. Один охранник на все провайдеры, и он в том же месте, где уже
   считается право на очередь (`src/lib/authz/guard.ts`).
3. **Фактор требуется роли, а не очереди.** `STAFF` и `OWNER` — да, `USER` —
   нет. Привязать требование к уровню `APPROVE` было бы тоньше, но сотрудник с
   `HANDLE` пишет заявителям от имени проекта и видит их документы: это тот же
   привилегированный доступ.
4. **Заведение фактора — дверь, а не настройка.** Сотрудник без фактора при
   входе в `/admin` попадает на страницу заведения и не может её обойти:
   «включу потом» означает «не включу». Владелец — так же; ему первому.
5. **Ключ в базе лежит зашифрованным** (AES-256-GCM, ключ из `.env`), а не
   открытым. Секрет TOTP нельзя хешировать — по нему считается код, — поэтому
   дамп таблицы без ключа приложения не должен давать второй фактор. Тот же
   ход мысли, что у токенов сброса пароля (в базе только sha256) и у приватного
   корня вложений: дамп не должен быть входом.
6. **Код нельзя использовать дважды.** У записи хранится номер последнего
   принятого шага (`lastStep`); код того же или более раннего шага отвергается.
   Без этого подсмотренный через плечо код годится все 30 секунд, а с
   допуском ±1 шаг — полторы минуты.
7. **Допуск ±1 шаг** (30 с назад и вперёд) — часы телефона уходят; больше
   означало бы расширять окно подсматривания.
8. **Десять кодов восстановления**, одноразовые, в базе только sha256,
   показываются **один раз** при заведении (как ссылка приглашения сотрудника).
   Потерянный телефон иначе означает потерянный доступ, а снимать фактор
   руками может только владелец — и у владельца, который и есть потерявший,
   этого пути нет.
9. **Ограничитель на проверку кода** — на тех же строках `LoginAttempt`
   с приставкой `__mfa__`: 10 неудач на запись за 15 минут. Шестизначный код
   при неограниченных попытках подбирается за сутки.
10. **Снять фактор может только владелец, с причиной, и это пишется в
    `AdminAuditLog`** (`DISABLE_STAFF_MFA`). Себе владелец снять не может —
    иначе выманенный у владельца пароль снимает и фактор.
11. **Штамп сеанса не стареет внутри сеанса.** Повторный ввод кода раз в N
    часов — отдельное решение, которое стоит принимать, когда появится жалоба;
    сейчас сеанс живёт ограниченное время сам, и повторный ввод только приучал
    бы вводить код не думая.

## Чего не берём, и почему

- **Passkeys (WebAuthn).** Строго лучше TOTP: фишинг-устойчивы, ничего не
  переписывается руками. Но это вторая реализация и привязка к устройству, и
  начинать с неё при одном владельце и трёх сотрудниках — поставить дверь,
  которую некому открывать. Берём TOTP, оставляя место: `StaffMfa.kind`
  (`TOTP`) делает вторую семью добавлением строки, а не переписыванием.
- **Фактор для обычных посетителей.** Их привилегий это не касается, а
  потерянный фактор у посетителя — поток обращений, который некому вести.
- **Доверенные устройства («не спрашивать 30 дней»).** Это ровно та поблажка,
  из-за которой второй фактор перестаёт существовать. Сеанс и есть доверие.
- **Второй фактор на отдельное действие** (подтверждение кодом каждого
  одобрения). У нас уже есть правило четырёх глаз — вторая подпись решает ту
  же задачу надёжнее, чем код, который человек наберёт механически.

## Данные

```
model StaffMfa {
  userId     String   @id
  kind       MfaKind  @default(TOTP)
  secretEnc  String            // AES-256-GCM: iv:tag:ciphertext, base64url
  confirmedAt DateTime?        // пока null — заведение не завершено
  lastStep   BigInt?           // номер принятого шага: повтор кода отвергается
  createdAt  DateTime @default(now())
  disabledAt DateTime?
  disabledById String?
  disabledReason String?
  user       User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model StaffMfaRecoveryCode {
  id        String   @id @default(cuid())
  userId    String
  codeHash  String            // sha256, как токен сброса пароля
  usedAt    DateTime?
  @@index([userId])
}

// Session: + mfaAt DateTime?
```

## Экраны

- `/{locale}/admin/*` — охранник: роль требует фактора, фактор не заведён →
  `/{locale}/mfa/setup`; заведён, но у сеанса нет штампа → `/{locale}/mfa`.
- `/{locale}/mfa/setup` — QR (отрисовывается у нас, без сторонней службы),
  ключ буквами на случай ручного ввода, поле кода для подтверждения, затем
  десять кодов восстановления одним экраном и кнопка «я записал».
- `/{locale}/mfa` — поле кода; ссылка «ввести код восстановления».
- `/{locale}/cabinet` — раздел «Вход и безопасность» у сотрудника: фактор
  заведён когда, сколько кодов восстановления осталось, «перевести на другой
  телефон» (заводится заново, прежний ключ гаснет).
- `/{locale}/admin/staff` — у строки сотрудника: есть ли фактор; у владельца
  кнопка «снять фактор» с причиной.

## Живой прогон (что обязательно проверить)

1. Сотрудник без фактора: `/admin` → страница заведения, обойти нельзя.
2. Заведение: код из приложения принят, сеанс получил штамп, `/admin` открылся.
3. Тот же код второй раз — отвергнут (`code_reused`).
4. Код с чужими часами (шаг ±2) — отвергнут, ±1 — принят.
5. Одиннадцатая неудача за 15 минут — 429.
6. Код восстановления: вход прошёл, код погас, второй раз не годится.
7. Вход через Google тем же сотрудником — фактор спрошен (провайдер не важен).
8. Владелец снял фактор сотруднику с причиной → строка в `AdminAuditLog`,
   сотрудник на входе в `/admin` снова на странице заведения.
9. Посетителя (`USER`) фактор не касается нигде.
