# Чтение сети для нативных Substrate-монет (слайс S)

**Дата:** 2026-11-07
**Разделы:** публичная карточка `/{locale}/coin/[slug]` (секции `#contracts`,
`#tokenomics`, `#acceptance`); кабинет карточки `/{locale}/cabinet/coins/[id]`; воркер

## Контекст

Слайсы B (сверка контрактов) и E (проверенный выпуск) умеют только EVM: оба
начинаются с `CoinCardContract` — сети и адреса токена. Монета, которая живёт
не токеном в чужой сети, а **нативной единицей собственной сети**, через эту
дверь не проходит: контракта у неё нет вообще.

Единственная карточка в базе — Taler (`TAL`) — ровно такая. Поэтому часовой
прогон `runSupplySweep()` честно возвращает `cards: 0`, общий выпуск вписан в
карточку руками (`1 434 102 859`, с пометкой в тексте «считан с узла 6 ноября
на блоке 13 936 804»), а платёжный профиль пуст. Все числа у монеты — с её же
слов, при том что сеть открыта и читается без чьего-либо разрешения.

Узел проверен живьём: `https://node.taler.uno` отвечает по обычному HTTP
JSON-RPC, без ключей и регистрации, и отдаёт всё, что нужно:

| Запрос | Ответ (7 ноября 2026) |
| ------ | --------------------- |
| `system_properties` | `ss58Format: 10960, tokenDecimals: 12, tokenSymbol: "TAL"` |
| `Balances.TotalIssuance` | `1 434 460 603 TAL` |
| `Timestamp.Now` на блоках `N` и `N−200` | **6,0 с** на блок |
| `chain_getHeader` vs `chain_getFinalizedHead` | отставание **2 блока ≈ 12 с** |
| `chain_getBlockHash(0)` | `0xb029803f…aaa96f` |
| `System.Account` через `blake2_128concat` | `AccountInfo` 80 байт, `free`/`reserved` декодируются |

## Принципы

Слайс наследует правила B и E целиком и добавляет одно своё.

1. **Нативная монета — не контракт.** Сущность «сеть монеты» вводится отдельно
   от `CoinCardContract`, а не притворяется контрактом с поддельным адресом.
   Идентичность сети — хэш генезиса, а не адрес.
2. **Ключи хранилища выводятся, а не вставляются.** `twox128` считается в коде,
   а тест сверяет вывод с опубликованными константами
   (`Balances.TotalIssuance`, `System.Account`). Магический хекс в исходнике
   невозможно перепроверить, а через год — и объяснить.
3. **Заявление проекта не правится.** Факт сети живёт в своей строке
   (`CoinCardSupply`, `CoinCardChainFacts`), а рядом показывается расхождение с
   заявленным. Правило B («не поправлять молча, а показывать расхождение»)
   остаётся в силе и для платёжного профиля: значения проекта в `payments` не
   перезаписываются, рендер **предпочитает** факт и подписывает его провенансом.
4. **Измеренное — не константа.** Время блока и задержка финализации получены
   замером на конкретных блоках, а не вычитаны из рантайма. Пишутся с номерами
   блоков и временем замера, показываются как «измерено на блоке N».
5. **Узел проекта — это и есть сеть.** У небольшой L1 нейтрального публичного
   RPC не существует; её собственный узел отдаёт каноническое состояние цепи,
   которое любой может перепроверить в эксплорере. Поэтому метка
   `VERIFIED_ONCHAIN` ставится, а в `source` пишется ключ сети. Реестр сетей —
   код, а не пользовательский ввод: проект не может подсунуть свой URL.

## Данные

### Привязка карточки к сети — одно поле

```prisma
model CoinCard {
  // …
  /// Ключ сети из реестра substrate-chains, если монета — нативная единица
  /// собственной сети. Контракта у такой монеты нет: идентичность сети —
  /// хэш генезиса, он лежит в CoinCardSupply.address и CoinCardChainFacts.
  nativeChain String?
}
```

Поле относится к разделу `CONTRACTS` (`SECTION_BY_ROOT.nativeChain = "CONTRACTS"`)
и потому **высокорисковое**: подмена значения переносит на карточку выпуск и
скорость чужой сети — тот же вектор, что подмена адреса контракта. Правка идёт
через ревизию и модератора, как и контракты.

Отдельной модели нет сознательно: у нативной монеты ровно одна домашняя сеть,
а реестр лежит в коде. `enum` тоже нет — добавление сети не должно требовать
миграции (так же решено для `chain` у контрактов и `kind` у рынков).

### Факты сети — новая модель

```prisma
model CoinCardChainFacts {
  id             String   @id @default(cuid())
  cardId         String   @unique
  card           CoinCard @relation(fields: [cardId], references: [id], onDelete: Cascade)
  chain          String
  genesisHash    String
  tokenSymbol    String?
  tokenDecimals  Int?
  ss58Format     Int?
  /// Измерено: (t(N) − t(N−k)) / k. Float, потому что 6,0 с — это замер.
  blockSeconds   Float?
  blockSample    Int?
  bestNumber     Int?
  finalizedNumber Int?
  finalityLag    Int?
  /// finalityLag × blockSeconds. Производное, но хранится: рендер не считает.
  finalitySeconds Float?
  /// SYMBOL | DECIMALS — расхождение сети с заявленным в карточке;
  /// CHAIN_SYMBOL | SS58_FORMAT — расхождение сети с реестром.
  mismatches     String[] @default([])
  checkedAt      DateTime
  /// chain_unsupported | rpc_unreachable | rpc_error | decode_failed | genesis_mismatch
  checkError     String?

  @@index([checkedAt])
}
```

Отдельно от `CoinCardSupply`: выпуск и скорость сети обновляются с разной
частотой, по разным причинам и читаются разными разделами карточки. Класть их в
одну строку значит переписывать выпуск при каждом замере времени блока.

`CoinCardSupply` **не меняется** — существующих полей достаточно:
`chain` = ключ сети (`"taler"`), `address` = хэш генезиса, `method` =
`"SUBSTRATE_V1"` вместо `"ONCHAIN_V1"`.

### Реестр сетей

```ts
export const SUBSTRATE_CHAINS = [
  { key: "taler",    label: "Taler",    defaultRpcUrl: "https://node.taler.uno",
    ss58Format: 10960, symbol: "TAL" },
  { key: "polkadot", label: "Polkadot", defaultRpcUrl: "https://rpc.polkadot.io",
    ss58Format: 0,     symbol: "DOT" },
  { key: "kusama",   label: "Kusama",   defaultRpcUrl: "https://kusama-rpc.polkadot.io",
    ss58Format: 2,     symbol: "KSM" },
] as const;
```

Все три проверены живьём по HTTP POST. Переопределение адреса —
`SUBSTRATE_RPC_TALER` и т.д.: публичный узел может начать банить сервер, как
это уже было со Stooq и Overpass. `ss58Format` и `symbol` в реестре —
ожидаемые значения: расхождение с ответом узла пишется в `mismatches`
(`SS58_FORMAT`, `CHAIN_SYMBOL`), а не принимается на веру.

## Что читаем и как

| Факт | Метод RPC | Ключ / приём |
| ---- | --------- | ------------ |
| Знаки, тикер, префикс SS58 | `system_properties` | — |
| Общий выпуск | `state_getStorage` | `twox128("Balances") ++ twox128("TotalIssuance")`, u128 LE |
| Баланс исключения | `state_getStorage` | `twox128("System") ++ twox128("Account") ++ blake2_128(pub) ++ pub`; берём `free + reserved` |
| Хэш генезиса | `chain_getBlockHash(0)` | — |
| Время блока | `state_getStorageAt` ×2 | `twox128("Timestamp") ++ twox128("Now")` на блоках `N` и `N−200`, u64 LE (мс) |
| Задержка финализации | `chain_getHeader`, `chain_getFinalizedHead` | разность номеров |

`free + reserved`, а не `free`: застейканное и забонденное в казне проекта всё
равно принадлежит казне и в оборот не входит. `frozen` не вычитается — в
нынешнем рантайме это подмножество `free`, и вычитание посчитало бы его дважды.

Канонические адреса сжигания (`0x0…0`, `0x…dEaD`) для Substrate **не
применяются**: в этой сети их нет, а Taler прямо заявляет, что сжигания нет —
слэшинг уходит в Казначейство.

## Поток

```
воркер 45-я минута — runSupplySweep()
  карточки с (канонический сверенный контракт) ИЛИ (nativeChain ≠ null)
    nativeChain → readSubstrateSupplyFacts
        system_properties → decimals
        TotalIssuance → totalUnits
        для каждого исключения (≤20) → System.Account → free+reserved
    → computeSupply (уже существует, чистая)
    → CoinCardSupply { chain, address: genesis, method: "SUBSTRATE_V1", … }
    → provenance["supply.circulating"] = VERIFIED_ONCHAIN / source: "taler"
    → CoinCardPriceIndex пересчитает капитализацию и FDV (слайс E, не меняется)

воркер 35-я минута — runChainFactsSweep()
  карточки с nativeChain ≠ null, ≤50 за прогон
    → system_properties, генезис, время блока, задержка финализации
    → сверка tokenSymbol с CoinCard.symbol и tokenDecimals с заявленными
    → CoinCardChainFacts
    → provenance["payments.blockSeconds"]    = VERIFIED_ONCHAIN
      provenance["payments.finalitySeconds"] = VERIFIED_ONCHAIN
```

Провенанс пишется в карточку, а значения — в `CoinCardChainFacts`: бейдж
«проверено в блокчейне» и само число берутся из разных источников, но ровно
одна строка рендера отвечает за выбор между фактом и заявлением.

## Как это видно

**Секция `#contracts`** — вместо нынешней пустоты для нативной монеты блок
«Сеть монеты»:

```
Сеть монеты         Taler                     [проверено в блокчейне]
Тикер в сети        TAL                       [проверено в блокчейне]
Знаков после точки  12                        [проверено в блокчейне]
Хэш генезиса        0xb029803f…aaa96f
Время блока         6,0 с  (измерено на блоке 13 947 996)
```

Расхождение тикера или знаков — красная строка «проект заявил X, сеть отвечает
Y», как у контрактов в слайсе B.

**Секция `#tokenomics`** — уже построенный блок проверенного выпуска начинает
работать: общий выпуск, вычтенные исключения, оборот, отклонение от
заявленного. Ничего в рендере не меняется, кроме подписи источника.

**Секция `#acceptance`, платёжный профиль** — две строки из шести перестают
быть словами проекта:

```
Окончательность платежа  ~12 с   [проверено в блокчейне]   проект заявил: 6 с
Время блока              6,0 с   [проверено в блокчейне]
```

Строка «проект заявил» появляется только при расхождении больше 10%.

**Кабинет** — в существующей секции «Проверенный выпуск» кнопка пересчёта
работает для нативной сети; ниже строка фактов сети с временем замера.

## Ошибки

Коды `CoinCardSupply.checkError` и `CoinCardChainFacts.checkError`:
`chain_unsupported` (ключ не в реестре), `rpc_unreachable`, `rpc_error`,
`decode_failed`, `supply_unreadable`, `decimals_unknown`, `address_invalid`
(SS58 не разбирается или префикс чужой), `genesis_mismatch` (хэш генезиса
отличается от сохранённого в прошлый прогон — значит узел переехал на другую
цепь; числа в этом случае не перезаписываются, нужен разбор руками).

Недоступный узел не стирает прошлые числа: сбой связи — не новость о монете.
Это правило слайса E (`createDefaults`) переносится без изменений.

## Тестирование

Чистые функции — модульно, без сети:

- `substrate-codec`: `twox128("Balances")` и `twox128("TotalIssuance")` дают
  опубликованные константы; то же для `System`/`Account`; `xxh64` на пустой
  строке и на строке длиннее 32 байт (разные ветки алгоритма); u128 LE на нуле,
  на максимуме и на нечётной длине; `AccountInfo` 80 байт → `free`/`reserved`;
  SS58 — валидный адрес, битая контрольная сумма, чужой префикс.
- `substrate-chains`: алиасы (`"Taler"`, `"taler"`, `"substrate"` → null),
  переопределение URL из окружения.
- `substrate-rpc`: все чтения на поддельном `fetchImpl` — успех, `rpc_error`,
  обрыв, мусор в ответе; время блока на двух подготовленных метках.
- `coin-card-chain-facts`: расхождение тикера и знаков, нулевая задержка
  финализации, отрицательная разность времени (узел отдал блоки не по порядку →
  `decode_failed`, а не отрицательное время блока).
- `coin-card-supply`: ветка `SUBSTRATE` на поддельном `fetchImpl`; исключение с
  SS58-адресом; EVM-ветка не задета (все 911 прежних тестов зелёные).

Живой прогон после сборки — обязателен: `node.taler.uno` отдаёт настоящие
числа, и выпуск в карточке Taler должен сойтись с эксплорером.

## Границы слайса

**Входит:** реестр Substrate-сетей, кодек и ключи хранилища, типизированные
чтения, привязка карточки к сети, проверенный выпуск для нативной монеты,
факты сети (тикер, знаки, генезис, время блока, задержка финализации),
расхождения с заявленным, рендер в трёх секциях, кабинет, воркер, 10 локалей.

**Не входит сознательно:**

- **Типичная комиссия перевода.** Честное чтение требует собрать экстринсик
  `balances.transfer_keep_alive` по метаданным рантайма и спросить
  `payment_queryInfo`. Это кодирование SCALE по динамическим индексам паллет —
  отдельная работа, и ошибка в ней даёт продавцу заниженную комиссию, то есть
  ровно тот вред, от которого раздел объявлен высокорисковым.
- `Balances.InactiveIssuance` — вычитание неактивного выпуска. Сначала нужно
  решение, считается ли он оборотом; сейчас `total` это `total`.
- Solana, TON, Cosmos — другие кодеки, другой слайс.
- Парачейны и чтение через WebSocket-подписки: HTTP-опроса раз в час хватает.
- Метаданные рантайма (`state_getMetadata`) — несколько сотен килобайт на
  запрос, и без них всё перечисленное читается.

## Порядок работы

Два захода, каждый — рабочее состояние в проде:

1. **Выпуск.** Кодек, реестр, чтения, `nativeChain`, ветка в прогоне выпуска,
   рендер выпуска, кабинет, живой прогон на Taler. Коммит.
2. **Факты сети.** `CoinCardChainFacts`, замер времени блока и финализации,
   расхождения, блок «Сеть монеты», платёжный профиль, воркер, локали. Коммит.

Остановка после первого захода оставляет систему полезной: Taler получает
проверенный выпуск, капитализацию и FDV.
