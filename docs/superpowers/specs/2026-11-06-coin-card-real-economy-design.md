# Карточка монеты для реального сектора: приём, платёжный профиль, путь к фиату, право (Слайс F)

**Дата:** 2026-11-06
**Раздел:** публичная карточка `/{locale}/coin/[slug]`; кабинет карточки
`/{locale}/cabinet/coins/[id]`; форма точки в бизнес-кабинете; каталог финтеха

## Контекст

Карточка после слайсов A1/A2 отвечает на вопросы инвестора: сколько монет, кто
команда, где торгуется, кто и что менял. Для реального сектора вопрос другой:
**могу ли я этим принимать оплату и что мне за это будет.**

Ответа сейчас нет, и это видно на живом примере. Карточка Taler (`/ru/coin/taler`)
опубликована, заполнена на 60%, подтверждена проектом — и по ней невозможно понять,
примет ли её кофейня, сколько будет стоить перевод в евро, через кого вывести
выручку на счёт и законно ли это в Польше.

**У нас есть то, чего нет ни у CoinMarketCap, ни у CoinGecko:** собственная база
точек, где крипту принимают физически (`CompanyPoint`, бизнес-кабинет,
Crypto Navigator), и каталог финтех-сервисов (`FintechCompany`) с поддерживаемыми
монетами, фиатами и странами. Эти две базы с карточкой не связаны вообще.

### Техническая причина разрыва

```
CompanyPoint.acceptedCoinIds  String[]   // id из CoinGecko (Coin.id)
FintechCompany.supportedCoinIds String[] // id из CoinGecko (Coin.id)
```

Собственная карточка — это `CoinCard` со своим `cuid` и `slug`, у неё
`coinId = null`, потому что в CoinGecko такой монеты нет. **Поэтому ни точка, ни
финтех-сервис физически не могут указать, что принимают Taler.** Форма точки
(`PointForm`) получает список монет из `readTop100()` — собственных карточек там
нет и быть не может.

## Принципы

1. **Карточка отвечает продавцу, а не только инвестору.** Блоки реального сектора
   стоят в карточке наравне с токеномикой, а не в сноске.
2. **Замкнутый цикл.** Карточка приводит продавца → продавец заводит точку →
   точка делает карточку ценнее. Кнопка «я принимаю эту монету» живёт на самой
   карточке, а не в глубине кабинета.
3. **Провенанс остаётся главным.** Число точек — агрегировано нами (`AGGREGATED`),
   комиссия и финальность сначала самозаявлены проектом (`SELF_REPORTED`), потом
   читаются из сети (`VERIFIED_ONCHAIN`). Метка у каждого значения, как и везде.
4. **Правовой блок — не юридическая консультация.** Мы показываем заявление
   проекта со ссылкой на источник и дату, а не наш вывод о законности. Формулировки
   и дисклеймер — часть спеки, а не вкусовщина реализации.
5. **Ноль — это ноль.** Если точек приёма нет, блок говорит «пока нигде не
   принимается» и предлагает стать первым, а не скрывается. Скрытый пустой блок
   читается как обман, когда пользователь найдёт его у другой монеты.
6. **Максимальный реюз.** `CompanyPoint`, `FintechCompany`, POI-фид навигатора,
   конвейер ревизий A2, бейдж провенанса, гейты прав по разделам.

## F1. «Где принимается»

### Данные

```prisma
model CompanyPoint {
  // ...существующие поля...
  acceptedCoinIds String[]   // как было: id монет CoinGecko
  acceptedCardIds String[]   // НОВОЕ: id собственных карточек (CoinCard.id)
  @@index([acceptedCardIds], type: Gin)
}

model FintechCompany {
  // ...существующие поля...
  supportedCoinIds String[]  // как было
  supportedCardIds String[]  // НОВОЕ
  @@index([supportedCardIds], type: Gin)
}
```

**Почему параллельный массив, а не join-таблица и не синтетическая строка в
`Coin`.** Синтетический `Coin` для каждой карточки загрязнил бы рейтинговую
таблицу — мы сознательно решили, что карточка без цены в рейтинг не попадает.
Join-таблица была бы нормальнее, но `acceptedCoinIds` уже денормализованный
массив, и вторая, другая по форме связь для того же смысла усложнит и форму
точки, и POI-фид. Параллельный массив того же вида — наименьшее зло и
нулевой риск для существующих данных. Магические строки вида `card:<id>`
внутри старого массива отвергнуты: они тихо ломают любой существующий
`acceptedCoinIds.includes(coin.id)`.

### Что считаем

`src/lib/coin-card-acceptance.ts` (чистые функции + один запрос):

```
getAcceptanceSummary(cardId) → {
  total: number,                       // APPROVED-точек, принимающих монету
  byCountry: { code, count }[],        // топ-10
  byType: { type: PointType, count }[],
  recent: { id, name, city, countryCode, type }[],  // 6 штук для превью
}
```
Только `status: APPROVED` — непроверенная точка не доказательство приёма.

### Публичная карточка

Новая секция `#acceptance` между «Рынки» и «Безопасность» — то есть выше
маркетинга, потому что для продавца это и есть главный факт. Содержимое:

- **Счётчик:** «принимают в N точках, K стран» с бейджем провенанса
  `AGGREGATED`, источник — «по базе Trientes», с датой.
- **Разбивка по типу** (магазин, кафе, банкомат, POS, офис продаж) и топ стран —
  те же ярлыки, что в навигаторе, без новых сущностей.
- **Шесть ближайших точек** списком, каждая ведёт на карту.
- **Кнопка «Открыть на карте»** → `/{locale}/crypto-map?coin=card:<id>` —
  навигатор фильтрует POI-фид по карточке.
- **Если точек ноль:** «Эту монету пока нигде не принимают» + кнопка стать первым.

### Кнопка «Я принимаю эту монету»

Живёт в той же секции, для всех посетителей. Ветвление по состоянию:

| Состояние посетителя            | Куда ведёт                                                          |
| ------------------------------- | ------------------------------------------------------------------- |
| не авторизован                  | `/login?next=/{locale}/coin/<slug>#acceptance`                        |
| INDIVIDUAL без компании         | `/business` (форма регистрации компании), после — назад на карточку   |
| COMPANY, есть компания          | `/cabinet/companies/<id>#add-point?card=<cardId>` — форма с преднабранной монетой |
| уже принимает в какой-то точке  | «вы принимаете в N точках» + ссылка на управление                     |

`PointForm` расширяется: список монет = топ-100 из `readTop100()` **плюс**
одобренные карточки (`listSelfListedCards()`), помеченные как собственный листинг.
Выбор карточки пишется в `acceptedCardIds`, выбор монеты — в `acceptedCoinIds`,
как и раньше.

### POI-фид навигатора

`/api/crypto-map/poi` уже домешивает `CompanyPoint` к зеркалу BTC Map. Добавляется
параметр `coin`: значение `card:<cardId>` фильтрует по `acceptedCardIds`, обычное
значение — по `acceptedCoinIds`. Фильтр применяется только к нашим точкам: в
зеркале BTC Map собственных карточек заведомо нет, и притворяться, что есть, нельзя.

### Виджет-бейдж для сайта продавца

`GET /{locale}/coin/[slug]/badge.svg` → статичный SVG «Принимаем TAL · trientes.org»
(цвета и типографика берутся из существующих токенов темы, новый визуальный язык не
изобретается). Рядом, в секции приёма, — поле со сниппетом для вставки:

```html
<a href="https://trientes.org/en/coin/taler"><img src="https://trientes.org/en/coin/taler/badge.svg" alt="Принимаем TAL"></a>
```

Кеш `public, max-age=86400`. Никакой телеметрии в бейдже — это чужой сайт.

## F2. Платёжный профиль

Новое значение enum `CoinCardSection.PAYMENTS` и новое поле `CoinCard.payments Json?`.
Раздел **высокорисковый** (`coin-card-risk.ts`): завышенная скорость или заниженная
комиссия — это решение продавца, принятое на ложных данных.

```jsonc
payments = {
  finalitySeconds: 6,            // когда платёж неотзывен
  blockSeconds: 6,
  tps: 1000,                     // заявленная пропускная способность
  feeUsdTypical: 0.004,          // типичная комиссия перевода, USD
  feeNote: "2% от эталонной сетки Substrate",
  reversible: false,             // есть ли возврат/чарджбэк на уровне сети
  stablecoins: ["USDT"],         // стабильные активы на этой сети, [] если нет
  integrations: [                // готовые интеграции для кассы и магазина
    { kind: "WOOCOMMERCE" | "SHOPIFY" | "1C" | "POS" | "SDK" | "OTHER",
      name: "…", url: "https://…" }
  ],
  refundPolicyUrl: null
}
```

**Что можно и нужно читать из сети, а не со слов проекта.** Для Substrate-сетей
(как Taler) по публичному RPC доступны: длительность блока, факт детерминированной
финальности, фактическая комиссия типичного перевода. Для EVM — цена газа и
стоимость обычного перевода. Это работа слайса B (чтение сети), но провенанс
закладывается здесь: в F2 поля заполняет проект с меткой `SELF_REPORTED`, а
воркер слайса B позже перезаписывает их с меткой `VERIFIED_ONCHAIN`. Правило
`mergeProvenance` уже гарантирует, что самозаявление не затрёт проверенное.

### Как это видно на карточке

Внутри секции `#acceptance`, подблоком «Платёжный профиль» — шесть строк,
каждая с бейджем провенанса:

```
Окончательность платежа   6 сек        [проверено в блокчейне]
Типичная комиссия         $0.004       [проверено в блокчейне]
Пропускная способность    1000 tx/сек  [заявлено]
Возврат средств           невозможен   [заявлено]
Стабильные монеты в сети  USDT         [заявлено]
Интеграции с кассами      WooCommerce, POS SDK
```

Строка «Возврат средств: невозможен» написана прямо и без смягчения: для продавца
это преимущество, для покупателя — риск, и обе стороны должны прочитать одно и то же.

## F3. Путь к фиату (после F1/F2)

Связка карточки с уже существующим каталогом финтеха через `supportedCardIds`.
На карточке — подблок «Как принять и вывести в деньги»:

- список сервисов, которые поддерживают эту монету: приём платежей / обмен /
  вывод на счёт, страны доступности (`availableIn`), фиаты (`supportedFiats`),
  уровень KYC (`kycLevel`), краткая сводка комиссий (`feesSummary`);
- каждый ведёт на карточку сервиса `/{locale}/fintech/[slug]`.

Новых полей у `FintechCompany` не требуется — всё уже есть, кроме связи.

## F4. Правовой статус по юрисдикциям (последний)

Новое поле `CoinCard.legal Json?`, раздел того же `PAYMENTS` или отдельный
`LEGAL` — решается при планировании F4.

```jsonc
legal = {
  disclaimer: true,              // блок всегда рендерится с дисклеймером
  jurisdictions: [
    { countryCode: "PL",
      status: "ALLOWED" | "LICENSED" | "RESTRICTED" | "BANNED" | "UNCLEAR",
      note: "Приём оплаты разрешён, VASC-регистрация для обмена",
      sourceUrl: "https://…",    // обязателен, иначе запись не принимается
      asOf: "2026-11-06" }
  ]
}
```

**Жёсткие правила блока:**
- запись без `sourceUrl` и `asOf` не сохраняется — утверждение о законе без
  источника и даты хуже, чем его отсутствие;
- раздел всегда высокорисковый и всегда проходит модератора, независимо от
  уровня доверия карточки;
- в интерфейсе — постоянный дисклеймер: это заявление проекта со ссылкой на
  источник, а не юридическая консультация Trientes;
- статус `UNCLEAR` — полноправный, а не отсутствие записи.

Это тот блок, который естественно продолжается проектом «Нигингур»: карточка
показывает статус, дальше человек идёт к юристу нужной юрисдикции.

## Границы слайса F

**Входит:** связь карточки с точками и финтехом, счётчик и карта приёма, кнопка
продавца, виджет-бейдж, платёжный профиль, правовой блок, их модерация через
существующий конвейер ревизий A2.

**Не входит:** приём платежей самим Trientes (мы не процессинг), расчёт
волатильности и калькулятор издержек продавца (отдельная история, нужна цена из
слайса C), автоматическая проверка юридических статусов, рейтинг сервисов
эквайринга, отзывы продавцов.

## Ошибки и валидация

Коды в едином стиле: `card_not_found`, `point_not_found`, `not_a_merchant`,
`coin_not_selectable` (карточка не одобрена — нельзя указать как принимаемую),
`finality_invalid` (не число или < 0), `tps_invalid`, `fee_invalid`,
`integration_url_invalid`, `legal_source_required`, `legal_date_required`,
`country_unknown`.

Лимиты: ≤20 интеграций на карточку; ≤60 записей юрисдикций; `feeNote` ≤200
символов; `note` юрисдикции ≤500 символов; счётчик точек считается на запрос без
кеша (как и POI-фид: одобрение точки должно быть видно сразу).

## Тестирование

Чистыми функциями, без базы:
- `coin-card-acceptance.ts` — агрегация по странам и типам, пустой случай, лимит превью;
- валидация `payments`: отрицательная финальность, нулевой TPS, кривой URL интеграции;
- валидация `legal`: запись без источника и без даты отклоняется, неизвестная страна отклоняется;
- фильтр POI-фида: `card:<id>` попадает только в наши точки и никогда в зеркало BTC Map.

Интеграционно: точка, одобренная после публикации карточки, немедленно
увеличивает счётчик (нет кеша); удаление карточки не оставляет висячих id в
`acceptedCardIds` (чистка при удалении карточки).

## Открытые вопросы, сознательно отложенные

- Нужен ли продавцу обратный виджет — «эта точка принимает TAL» на карточке точки
  (сейчас точка показывает только принимаемые монеты списком).
- Считать ли оборот в монете по точкам (продавцы вряд ли захотят его раскрывать).
- Показывать ли на карточке монеты список компаний-партнёров отдельно от точек
  (B2B-приём без физического адреса — услуги, аренда, опт).
