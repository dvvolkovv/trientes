# Роль комплайнса: права по очередям, приглашение сотрудника, настоящая вторая подпись

Дата: 2026-11-17. Слайс **AS**. Спека-предшественник — `2026-11-17-compliance-case-management-design.md`
(управление делами), от неё остался незакрытый пункт: «Ролей комплайнса по-прежнему нет».

## Задача

Владелец (`biotecbank`) нанимает сотрудников комплайнса и хочет в момент приглашения
отмечать, **что человек делает, за какие разделы отвечает и имеет ли право решать** —
включая право на вторую подпись. Сегодня этого нельзя: в системе два значения роли
(`USER`, `ADMIN`), и `ADMIN` — это полные ключи от всего.

## Что есть сегодня (факты из кода)

- `Role { USER, ADMIN }` (`prisma/schema.prisma:10`). Третьего значения нет.
- Любой `ADMIN` делает админом любого (`src/lib/admin/set-user-role.ts`), защита только
  от снятия **последнего** админа.
- Охранник один и грубый: `checkAdmin()` (`src/lib/is-admin.ts`) — **58 вызовов в 24 файлах**.
  Он отвечает на единственный вопрос «ты админ или нет».
- Очередей дел восемь (`src/lib/cases/queues.ts`): `coinCards`, `companies`, `points`,
  `exchanges`, `fintech`, `kyb`, `coinRequests`, `pointReports`.
- Правило четырёх глаз различает **людей**, а не роли (`src/lib/cases/approval.ts`):
  «кому можно утвердить вместо проверившего» считается как
  `prisma.user.count({ where: { role: "ADMIN", id: { not: reviewedById } } })`.
  В базе три `ADMIN`, и все три — записи владельца, поэтому правило сейчас **показное**:
  проверить можно одной записью, утвердить другой, и журнал напишет «подписали двое».
- Приглашения в команду предприятия и в команду карточки монеты уже есть
  (`src/lib/invite-tokens.ts`, `src/app/actions/company-invites.ts`) — приглашений
  сотрудника нет.

## Практика, которая берётся

Выбрано по принципу «уместный современный стандарт», а не «самый мощный инструмент».

**Берём:**

1. **Право — тройка «кто / где / сколько»** (`userId` × очередь × уровень). Так устроены
   назначения в Azure RBAC и permission sets в AWS IAM. Права «на человека целиком»
   (один флажок «может решать» на все восемь очередей) — практика десятых годов: она не
   умеет сказать «по биржам решает, по карточкам монет только готовит».
2. **Запрет по умолчанию, минимум прав** (least privilege, SOC 2 CC6.1). Нет строки
   права — нет доступа. Новый сотрудник не видит ни одной очереди, пока владелец не выдал.
3. **Разделение обязанностей считается по очереди** (maker-checker, как в Sumsub/Alloy):
   второй подписью считается только тот, у кого есть право **утверждать именно в этой
   очереди**. Это и починит показное правило четырёх глаз.
4. **Запрет конфликта интересов** (атрибутное ограничение поверх ролей): нельзя вести и
   решать дело объекта, с которым ты связан — ты участник этого предприятия, участник
   этой карточки, или ты сам подал заявку.
5. **Одна точка решения о праве** (разделение политики и охранника, PDP/PEP). Политика —
   чистая функция в `src/lib/authz/policy.ts`, накрытая тестом; охранники в действиях и
   на страницах только спрашивают её. Пятьдесят восемь разнородных проверок — это
   пятьдесят восемь мест, где можно забыть.
6. **У доступа есть срок и периодический пересмотр** (SOC 2 CC6.2–6.3, ISO 27001 A.5.18,
   требование периодической ревизии прав в DORA). У права может быть дата окончания;
   раз в шесть месяцев владельцу приходит напоминание пересмотреть, у кого какие права.
   Механика в проекте уже обкатана — так пересматриваются залистованные предприятия (AR).
7. **Доступ отзывается, человек не удаляется.** Отзыв — отметка на записи сотрудника, а не
   снос строк: иначе в журнале пропадёт, кто принимал решения.
8. **Приглашение — это пакет доступа** (как access packages в Microsoft Entra): права
   отмечаются в момент приглашения и применяются в момент принятия. Плюс готовые
   должности одной кнопкой — чтобы типовой найм не собирался галочками с нуля.
9. **Неизменяемый журнал выдачи прав**: кто, кому, что, когда — в `AdminAuditLog`.

**Не берём, и почему:**

- **Отдельный сервер политик** (Zanzibar-модель: OpenFGA, SpiceDB). Оправдан на сотнях
  типов объектов и отношений между ними. У нас восемь очередей и четыре уровня — это
  одна чистая функция и одна таблица.
- **Второй фактор на привилегированных действиях.** Настоящий стандарт для доступа
  такого уровня, но второго фактора в проекте нет ни у кого вообще — это отдельный слайс
  (рекомендован следующим в этой линии), а не приписка к этому.
- **Запрос доступа сотрудником с одобрением владельцем** (access request workflow). У нас
  один выдающий и единицы сотрудников; форма запроса — лишний круг.
- **Разделение прав внутри очереди по типу объекта** (например «только карточки Substrate»).
  Нет такого запроса, и уровень на очередь уже отвечает на вопрос владельца.

## Модель прав

### Роли

`Role { USER, STAFF, OWNER }` — плюс `ADMIN`, оставленный в типе как **наследие**.

- `OWNER` — владелец. Все очереди на уровне «утверждает» неявно, плюс то, что не является
  делом: права сотрудников, пользователи, аудит, аналитика, каталог монет.
- `STAFF` — сотрудник. Может **ровно то, что выдано** строками прав.
- `USER` — посетитель. В `/admin` не входит.
- `ADMIN` читается политикой как `OWNER` (`isOwnerRole`). Значение из enum в Postgres
  убрать внутри одной миграции нельзя, а оставить его «без прав» значило бы превратить
  живую запись владельца в бесправную при первом же промахе. Мост описан в коде и накрыт
  тестом; `ADMIN_WHITELIST` с этого слайса пишет `OWNER`.

### Уровни

`StaffLevel { VIEW, HANDLE, APPROVE }`; отсутствие строки = нет доступа.

| Уровень | Что можно |
|---|---|
| нет строки | очередь не видна на плитках, список и дело не открываются |
| `VIEW` | список очереди, дело, переписка, лист проверок, документы — только чтение |
| `HANDLE` | взять дело и отпустить, писать заявителю, отмечать пункты листа, вердикт по документу, правка времени, подпись «проверил» |
| `APPROVE` | всё из `HANDLE` + «Одобрить» / «Отклонить» (вторая подпись) и надзор своего типа: предупредить, снять, вернуть, «пересмотр пройден» |

`HANDLE` включает `VIEW`, `APPROVE` включает `HANDLE` — уровни упорядочены, политика
сравнивает порядок, а не перечисляет.

### Что остаётся за владельцем

Экраны, которые делами не являются: `/admin/users` (и выдача ролей), `/admin/audit`,
`/admin/analytics`, `/admin/coins`, `/admin/staff` (труд сотрудников и выдача прав).
Причина у всех одна: это не работа по заявке, а управление системой и людьми.

## Данные

Миграции пишутся руками и применяются `prisma migrate deploy` (чекаут — прод; `migrate dev`
умеет предлагать сброс базы).

**`20261118120000_staff_roles`** — `ALTER TYPE "Role" ADD VALUE 'STAFF'` и `'OWNER'`.

**`20261118121000_staff_roles_backfill`** — `UPDATE "User" SET role='OWNER' WHERE role='ADMIN'`.
Отдельной миграцией: новое значение enum нельзя использовать в той же транзакции, где оно
добавлено.

**`20261118130000_staff_access`**:

```prisma
enum StaffLevel { VIEW HANDLE APPROVE }

/// Запись сотрудника: должность словами, срок пересмотра доступа, отзыв.
/// Отдельная таблица, а не поля в User: у посетителя их нет и быть не должно.
model StaffMember {
  id             String    @id @default(cuid())
  userId         String    @unique
  user           User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  /// Должность: «старший проверяющий». Показывается в аналитике и в деле.
  title          String?
  /// Обязанности своими словами — то, что владелец пишет при приглашении.
  duties         String?
  invitedById    String?
  startedAt      DateTime  @default(now())
  /// Когда владельцу напомнить пересмотреть права (SOC 2 / ISO 27001).
  accessReviewAt DateTime
  /// Доступ отозван. Строка остаётся: журнал решений должен читаться.
  revokedAt      DateTime?
  revokedById    String?
  revokeReason   String?
}

/// Право на одну очередь. Нет строки — нет доступа.
model StaffGrant {
  id          String     @id @default(cuid())
  userId      String
  user        User       @relation(fields: [userId], references: [id], onDelete: Cascade)
  /// Ключ очереди из `src/lib/cases/queues.ts`. Строка, не enum: список очередей —
  /// дело кода, и новая очередь не должна требовать миграции.
  queue       String
  level       StaffLevel
  /// Необязательный срок: доступ «до конца проверки» не живёт вечно.
  expiresAt   DateTime?
  grantedById String?
  createdAt   DateTime   @default(now())
  updatedAt   DateTime   @updatedAt

  @@unique([userId, queue])
  @@index([queue, level])
}

/// Приглашение сотрудника: пакет доступа в одной строке.
model StaffInvite {
  id          String    @id @default(cuid())
  /// Только sha256 ссылки: дамп таблицы не должен давать доступ к админке.
  tokenHash   String    @unique
  /// Кому предназначено, если звали по адресу или логину. Для открытой ссылки — null.
  identifier  String?
  title       String?
  duties      String?
  /// Отмеченные при приглашении права: [{ queue, level, expiresAt? }].
  grants      Json
  invitedById String
  createdAt   DateTime  @default(now())
  expiresAt   DateTime
  acceptedAt  DateTime?
  acceptedById String?
  revokedAt   DateTime?

  @@index([invitedById])
}
```

Плюс `AdminNotificationKind += ACCESS_REVIEW_DUE` и
`AdminAction += STAFF_INVITED, STAFF_INVITE_REVOKED, STAFF_ACCESS_CHANGED, STAFF_ACCESS_REVOKED, STAFF_ACCESS_RESTORED, ACCESS_REVIEW_PASSED`
(миграция `20261118140000_staff_access_enums`), `targetType` аудита пополняется `"StaffInvite"`.

## Точка решения о праве

**Политика** — `src/lib/authz/policy.ts`, чистые функции без Prisma:

```ts
export type ViewerAccess = {
  userId: string;
  role: "USER" | "STAFF" | "OWNER" | "ADMIN";
  revokedAt: Date | null;
  grants: { queue: string; level: StaffLevel; expiresAt: Date | null }[];
};

isOwnerRole(role): boolean                    // OWNER или наследие ADMIN
levelFor(access, queue, now): StaffLevel|null // owner → APPROVE; отозван → null; истёкший грант → null
can(access, queue, need, now): boolean        // порядок уровней
visibleQueues(access, now): QueueKey[]        // плитки и полоса закладок
canOwnerOnly(access): boolean
```

**Охранник** — `src/lib/authz/guard.ts` поверх Prisma:

```ts
loadViewerAccess(): Promise<ViewerAccess | null>   // один запрос, обёрнут React cache()
requireQueue(queue, need): Promise<{ ok: true; userId: string } | { ok: false; reason: ... }>
requireOwner(): ...
```

`checkAdmin()` остаётся как `requireStaff()` — «вошёл, сотрудник или владелец, доступ не
отозван»: это базовая калитка в `/admin`, личные колокольчики и биение страницы ею и
ограничиваются.

**Никакого обхода охранника изнутри.** `applyDecision` (`src/lib/cases/decide.ts`) зовёт
те же серверные действия старых экранов, и каждое из них проверяет право **своей** очереди
по собственной сессии. Передавать «уже проверенного актёра» аргументом нельзя: серверное
действие — публичная поверхность, такой аргумент подделал бы кто угодно.

Единственное место, где очередь объекта и очередь дела расходятся, — дело жалобы
(`POINT_REPORT`), чьё решение снимает или возвращает **точку**. Поэтому надзор над точкой
требует `APPROVE` в `points` **или** в `pointReports`: обе очереди про один и тот же объект.

### Карта прав по экранам и действиям

| Экран / действие | Нужно |
|---|---|
| `/admin`, `/admin/queues` | сотрудник; плитки — только выданные очереди |
| `/admin/queues/[queue]`, `/admin/cases/[id]` | `VIEW` в этой очереди |
| `claimCase`, `releaseCase`, `caseHeartbeat`, `adjustCaseTime` | `HANDLE` |
| `sendStaffMessage`, `setCaseCheck`, `setDocumentVerdict` | `HANDLE` |
| `markReviewed` | `HANDLE` |
| `decideCase` | `APPROVE` |
| `approve*` / `reject*` старых экранов (`admin-coin-cards`, `admin-company`, `admin-points`, `admin-exchange`, `admin-fintech`, `admin-requests`, `kyb`) | `APPROVE` в соответствующей очереди |
| надзор точки (`point-supervision`) | `APPROVE` в `points` или `pointReports` |
| надзор предприятия (`company-supervision`) | `APPROVE` в `companies` |
| правки/удаления/восстановления на старых экранах (`admin-coin-revisions`, курируемый финтех, удаление и восстановление точек и предприятий) | `APPROVE` в соответствующей очереди |
| `/admin/notifications` | сотрудник (свои звонки) |
| `/admin/staff`, выдача прав, приглашения | владелец |
| `/admin/users`, `setUserRole` | владелец |
| `/admin/audit`, `/admin/analytics`, `/admin/coins` | владелец |
| история решений на старых экранах (вкладки approved/rejected) | `VIEW` в своей очереди |

Полоса закладок `/admin` показывает только доступное: сотруднику без прав на каталог
монет закладка «Coins» не рисуется. Прямой переход всё равно проверяется на сервере —
скрытая ссылка не защита.

## Разделение обязанностей

Правка `src/lib/cases/approval.ts`: `otherApproversCount` считается запросом

```
StaffGrant: queue = <очередь дела>, level = APPROVE,
  user.revokedAt = null, (expiresAt = null OR expiresAt > now), userId != reviewedById
+ число владельцев (OWNER), кроме проверившего
```

Отсюда:

- Сотрудник с `HANDLE` второй подписью **не считается** — и правило четырёх глаз
  перестаёт быть декорацией.
- `soleSignOff` срабатывает честно: один утверждающий в очереди — решение проходит с
  отметкой «утверждено одним лицом», как и описано в AP.

**Конфликт интересов** — `src/lib/authz/conflict.ts`, одна функция на все типы дел:

| Связь | Как ищется |
|---|---|
| сотрудник подал эту заявку | `ComplianceCase.applicantUserId == userId` |
| сотрудник в команде этого предприятия | `CompanyMember` по `COMPANY` / `KYB`, по компании точки для `POINT` / `POINT_REPORT` |
| сотрудник в команде этой карточки | `CoinCardMember` по `COIN_CARD` |

Связь блокирует всё изменяющее (взять дело, писать, отмечать, подписать, решить) с кодом
`conflict_of_interest`; чтение остаётся — запретить смотреть незачем, а знать причину
отказа полезно. Блокировка пишется в журнал дела не событием, а просто отказом: события
журнала — о заявке, а не о промахах сотрудника.

## Приглашение сотрудника

Экран `/admin/staff` получает второй раздел «Сотрудники и доступ» (только владелец):
список сотрудников (должность, очереди с уровнями, срок пересмотра, отзыв), список
активных приглашений и форма приглашения.

Форма: матрица 8 очередей × 4 уровня (`нет / смотрит / ведёт / утверждает`), поле должности,
поле обязанностей, необязательная дата окончания доступа, четыре готовые должности одной
кнопкой:

| Должность | Что ставит |
|---|---|
| Только чтение | `VIEW` во всех восьми |
| Проверяющий | `HANDLE` в `coinCards`, `coinRequests`, `points`, `pointReports`; `VIEW` в остальных |
| Старший проверяющий | `APPROVE` во всех восьми |
| KYB-офицер | `APPROVE` в `kyb` и `companies`; `VIEW` в `points`, `pointReports` |

Готовая должность — это только заполнение матрицы, после неё галочки правятся руками.

Две двери, как в командах предприятий:

- **по логину или адресу** — если запись уже есть: права выдаются сразу, человеку уходит
  `notifyUser` на языке его кабинета;
- **ссылкой** — `/{locale}/staff-invite/[token]`: 14 дней, одноразовая, ≤20 активных,
  отзывается владельцем, в базе только sha256. У гостя — ссылки на вход и регистрацию с
  `?next=`, после регистрации он возвращается на страницу приглашения.

Принятие (`acceptStaffInvite`): условный `updateMany` по `acceptedAt: null` (гонку двух
переходов снимает тот же приём, что в командах предприятий) → `StaffMember` с
`accessReviewAt = +6 месяцев` → строки `StaffGrant` → `Role: USER → STAFF` (владельца не
понижаем) → строка аудита `STAFF_INVITED`/принятие → `notifyUser` владельцу.

Правка прав существующему сотруднику — та же матрица на его строке; каждое изменение
пишет `STAFF_ACCESS_CHANGED` с прежним и новым уровнем. Отзыв (`STAFF_ACCESS_REVOKED`)
требует причины (≥3 символа, тот же порог, что у отказов) и действует немедленно: доступ
читается из базы на каждом запросе, перезаход не нужен. Возврат — `STAFF_ACCESS_RESTORED`.

**Нельзя выдать себе** (`self_grant`) и **нельзя отозвать владельца** (`owner_target`):
выдача — дело владельца, а владелец не сотрудник. Защита «последнего владельца» из
`set-user-role.ts` переименовывается в `last_owner` и остаётся.

## Срок и пересмотр доступа

- Истёкший `StaffGrant.expiresAt` перестаёт действовать сам — проверка в политике, а не в
  прогоне: прогон мог бы не состояться, и право прожило бы лишний день.
- `runStaffAccessReviewSweep()` (`src/lib/staff-access-sweep.ts`, воркер `45 5 * * *` —
  сразу после пересмотра предприятий): у сотрудника с `accessReviewAt <= now` и не
  отозванным доступом звонит `ACCESS_REVIEW_DUE` **владельцам** (у сотрудника нет права
  пересматривать себя), один повод на сотрудника не плодится — непрочитанный звонок
  обновляется (приём из AO).
- Кнопка «Пересмотр пройден» на строке сотрудника: `accessReviewAt = +6 месяцев`, аудит
  `ACCESS_REVIEW_PASSED`. Полгода — обычная частота ревизии доступа в SOC 2 и ISO 27001;
  отдельного интервала «высокого риска» у сотрудника нет (у предприятия он выводится из
  `risk`, у человека такого поля нет и придумывать его незачем).

## Переводы

Новые пространства: `admin.staff.access.*` (список, матрица, должности, отзыв, пересмотр),
`admin.staff.invite.*`, `staffInvite.*` (страница приёма ссылки), `notify.staffAccess.*`
(письмо сотруднику и владельцу), плюс коды отказов в `admin.errors.*`:
`no_access`, `conflict_of_interest`, `self_grant`, `owner_target`, `last_owner`.

Строки сотруднику и приглашённому — на языке **их** кабинета (прецедент: письмо сброса
пароля и заготовки ответов в AO). Служебные тексты звонков владельцу — по-английски, как
во всех прежних вызовах `notifyUser`.

После правки `messages/en.json` — `npm run i18n` (иначе интерфейс выйдет на сайт
по-английски: загрузчик подмешивает английский как базу).

## Испытания

Политика и правила — юнит-тестами, без базы:

- порядок уровней: `APPROVE` ⊃ `HANDLE` ⊃ `VIEW`; нет строки — нет доступа;
- владелец видит все очереди; `ADMIN` читается как владелец; отозванный — ничего;
- истёкший грант не действует, грант без срока действует;
- `visibleQueues` отдаёт только выданное;
- `otherApproversCount`: `HANDLE` второй подписью не считается, `APPROVE` в чужой очереди
  не считается, отозванный и истёкший не считаются;
- `soleSignOff` при единственном утверждающем;
- конфликт интересов по каждой из трёх связей;
- карта прав: у каждого экрана и каждого действия из таблицы есть требование, и нет
  требования без экрана (тот же приём, что у листов проверок в AP);
- готовые должности: каждая ставит уровень каждой из восьми очередей;
- `messages-parity` — как для любой правки английского файла.

## Границы слайса

Нет и в этом слайсе не будет: второго фактора входа (отдельный слайс, рекомендован
следующим), запроса доступа сотрудником, прав внутри очереди по типу объекта, сервера
политик, ограничения по адресу или времени суток, делегирования прав владельца другому
владельцу. Старые экраны очередей не переделываются — им только добавляются охранники по
той же карте.

## Живой прогон (что проверить на проде)

1. Завести временного сотрудника приглашением-ссылкой с правами «`HANDLE` в `coinCards`,
   `VIEW` в `exchanges`» → он видит две плитки из восьми, по карточкам может взять дело и
   подписать «проверил», «Одобрить» погасло, по биржам читает и не меняет, в
   `/admin/users` и `/admin/audit` не попадает.
2. Он ставит первую подпись → владелец утверждает: `soleSignOff = false`, в журнале два
   разных человека.
3. Снять у него `coinCards` → страница дела перестаёт открываться **без перезахода**.
4. Выдать `APPROVE` с датой окончания в прошлом → доступа нет.
5. Сделать его участником предприятия и открыть дело этого предприятия → `conflict_of_interest`.
6. Отзыв доступа → `/admin` не открывается; строки аудита `STAFF_*` на месте; его решения
   в `/admin/staff` по-прежнему посчитаны.
7. `accessReviewAt` в прошлое → прогон звонит владельцу один раз, повторный молчит;
   «Пересмотр пройден» переносит срок на полгода.
8. Убрать временного сотрудника и приглашение за собой.

Отдельно, не кодом: понизить две дублирующие записи владельца до `USER`, оставив
`biotecbank` (он в `ADMIN_WHITELIST`, повышение выживет). Пока записей три, правило
четырёх глаз обходится одним человеком.
