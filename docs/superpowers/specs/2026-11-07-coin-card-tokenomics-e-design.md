# Токеномика карточки: проверенный выпуск, капитализация, аллокация, разлоки (Слайс E)

**Дата:** 2026-11-07
**Раздел:** публичная карточка `/{locale}/coin/[slug]` (шапка и секция
«Токеномика»); кабинет карточки `/{locale}/cabinet/coins/[id]` (секция
TOKENOMICS и кнопка пересчёта); воркер

## Контекст

В карточке с слайса A есть три числа — `tokenomics.circulating`, `total`,
`max` — и тексты про эмиссию и сжигание. Все они **самозаявлены проектом**:
проект вписал их руками, провенанс `SELF_REPORTED`.

Из-за этого слайс C сознательно не считает капитализацию (см. его план,
отклонение 3): умножать свою честную медианную цену на цифру, набранную
проектом с клавиатуры, — значит выдать за расчёт то, что расчётом не является.
Капитализация — главное число, по которому монеты сравнивают и сортируют, и
именно его чаще всего накручивают: достаточно завысить circulating supply.

Этот слайс закрывает последний внешний провал в цепочке «свои данные»:
собственный выпуск читается из сети так же, как слайс B читает `totalSupply`, и
цена слайса C наконец умножается на проверенное число. Плюс два раздела, которые
слайс A предусмотрел в модели, но оставил пустыми: аллокация по долям и
календарь разлоков.

## Принципы

1. **Циркулирующий выпуск — вычитание, а не слово проекта.** `totalSupply` из
   контракта минус балансы адресов, которые по заявлению проекта не в обороте
   (казна, фонд, вестинг-контракты, адреса сжигания). Каждое слагаемое видно
   читателю с адресом и балансом — расчёт воспроизводим вручную.
2. **Заявление проекта не затирается.** Как в слайсе B: факт сети пишется в
   отдельную модель, расхождение показывается рядом. Если проект заявил 100 млн,
   а по сети 420 млн — читатель видит обе цифры и сам делает вывод.
3. **Капитализация показывается всегда, но честно подписанной.** Нет адресов
   исключений → считаем по самозаявленному выпуску и ставим метку «по данным
   проекта» (решение владельца). Скрывать число — значит делать карточку
   бесполезной для сравнения; метка решает ту же задачу без обмана.
4. **Список исключений — ответственность проекта, проверка — наша.** Проект
   указывает, какие адреса не в обороте; мы не угадываем за него. Но два
   канонических адреса сжигания (`0x0`, `0x…dEaD`) вычитаются всегда: никто не
   считает сожжённое оборотом.
5. **Разлоки вводятся руками** (решение владельца). Чтение контрактов локеров
   (Unicrypt, Team Finance, Sablier) — отдельный слайс: у каждого свой ABI, и
   половина проектов локает в самописных контрактах.
6. **Аллокация и разлоки весят в полноте карточки** (решение владельца) —
   иначе их не заполнит никто.

## Как считается выпуск

```
total       = totalSupply() канонического контракта / 10^decimals
excluded    = Σ balanceOf(адрес) по списку исключений / 10^decimals
circulating = max(0, total − excluded)
cap         = индексная цена × circulating
fdv         = индексная цена × (max ?? total)
```

Канонический контракт — тот, у которого `isCanonical = true` и `verifiedAt`
поставлен слайсом B. Без него считать нечего: подделка с тем же тикером
ответит на `totalSupply()` что угодно. Карточка без проверенного контракта
остаётся на самозаявленных числах с меткой `SELF_REPORTED`.

`balanceOf(address)` — селектор `0x70a08231` плюс адрес, выровненный в 32
байта. Один `eth_call` на адрес, не больше 20 адресов на карточку: публичные
узлы не для обстрела. Адрес, который не ответил, не обнуляет расчёт — он
попадает в список исключений со своей ошибкой, а его баланс в сумму не входит;
рядом с результатом стоит пометка «частичный расчёт», чтобы недоступный узел не
выглядел как «на этом адресе ноль».

**Единицы.** `totalSupply` в минимальных единицах — uint256, в `number` не
влезает. Читаем как десятичную строку (уже так сделано в слайсе B) и делим на
`10^decimals` строковой арифметикой: `unitsToCoins("420000000000000000000", 18)`
→ `"420"`. Для капитализации строка приводится к `number` — потери точности в
15-м знаке на показе цены в долларах неважны, в базе остаётся строка.

## Данные (одна аддитивная миграция)

```prisma
/// Факт сети о выпуске: что ответили контракт и адреса исключений.
/// Отдельная модель, а не поля в CoinCard — заявление проекта лежит в
/// tokenomics и не должно затираться фактом (правило слайса B).
model CoinCardSupply {
  id            String   @id @default(cuid())
  cardId        String   @unique
  card          CoinCard @relation(fields: [cardId], references: [id], onDelete: Cascade)
  chain         String
  address       String
  decimals      Int
  /// Десятичные строки в монетах, не в минимальных единицах.
  totalSupply   String
  excludedTotal String
  circulating   String
  /// [{address, label, balance, error}] — из чего сложилось excludedTotal.
  excluded      Json
  /// Хотя бы один адрес не ответил: расчёт неполный, в карточке об этом сказано.
  partial       Boolean  @default(false)
  /// Отклонение заявленного circulating от посчитанного, в процентах.
  claimedDeltaPct Float?
  method        String   @default("ONCHAIN_V1")
  checkedAt     DateTime
  checkError    String?

  @@index([checkedAt])
}
```

К `CoinCardPriceIndex` добавляются три поля — капитализация считается там же,
где цена, и обновляется с ней вместе каждые 10 минут:

```prisma
  marketCapUsd Float?
  fdvUsd       Float?
  /// ONCHAIN | SELF_REPORTED — чем мерили выпуск. Решает метку в карточке.
  supplySource String?
```

Полей для аллокации и разлоков в схеме не появляется: это `tokenomics` JSONB,
который слайс A уже завёл ровно под это (`allocation[]`, `unlocks[]` в его
спеке).

## Форма: исключения, аллокация, разлоки

**Исключения.** Сейчас `tokenomics.excludedAddresses` — список строк (поле
`lines`). Для расчёта нужен адрес, для показа — подпись «что это за кошелёк».
Поле становится `tokenomics.excluded` — строки `{address, label}`. Старое
`excludedAddresses` читается как `{address, label: null}` и не переписывается:
тот же приём, что с `burn` / `burnMechanism` в текущей секции токеномики.

**Аллокация** — `tokenomics.allocation[]`, строки
`{label, pct, cliffMonths?, vestingMonths?, address?}`. Правила: ≤20 строк,
`label` обязателен, `pct` в диапазоне 0…100, сумма ≤ 100 (с допуском 0.5 на
округления) — больше → ошибка `allocation_over_100`. Если сумма меньше 100,
остаток рисуется как «не распределено», а не прячется.

**Разлоки** — `tokenomics.unlocks[]`, строки
`{date, amount?, pct?, label, source?}`. Правила: ≤50 строк, дата парсится,
задан либо `amount` (в монетах), либо `pct` (от общего выпуска) — иначе
`unlock_invalid`. Строки сортируются по дате при нормализации.

## Как это видно

**Шапка карточки** (под ценой индекса): `Капитализация $X · FDV $Y` с меткой
провенанса — `AGGREGATED` (цена из N рынков × проверенный выпуск) или
`SELF_REPORTED` (выпуск по данным проекта).

**Секция «Токеномика»:**

1. Три плитки выпуска. Циркулирующий — проверенное число с меткой
   `VERIFIED_ONCHAIN`; если заявление проекта расходится больше чем на 1%,
   под ним строка «проект заявляет: N». Общий выпуск — из контракта.
2. Раскрывающийся расчёт: `total − Σ исключения = circulating`, адреса с
   балансами, подписями и ссылками на эксплорер, время проверки, пометка
   «частичный расчёт», если адрес не ответил.
3. Аллокация: горизонтальная полоса-стопка по долям и таблица с процентом,
   клиффом и вестингом. Строки без `pct` в полосу не попадают.
4. Разлоки: строка «в ближайшие 30 дней разлочится X% выпуска, за 90 — Y%»,
   ближайшие пять событий таблицей, прошедшие сворачиваются в счётчик.
5. Методика (эмиссия, сжигание) — как сейчас.

**Кабинет карточки:** в секции TOKENOMICS — редакторы исключений, аллокации и
разлоков; кнопка «Пересчитать выпуск» рядом с кнопкой пересверки контрактов,
результат и ошибка последней проверки под ней.

## Кадансы

- Воркер: `runSupplySweep()` раз в час (`45 * * * *`), до 50 карточек за
  прогон, очередь от самых давно не проверенных. Выпуск меняется редко — чаще
  незачем, а `eth_call` по 20 адресам на карточку это уже 1000 запросов.
- Капитализация и FDV пересчитываются внутри `syncCardMarkets` (каждые 10
  минут), потому что меняется цена, а не выпуск.
- Кнопка в кабинете — ручной пересчёт одной карточки, не чаще раза в 5 минут.

## Ошибки

`unauth`, `card_not_found`, `no_canonical_contract` (нет контракта с
`isCanonical`), `contract_unverified` (контракт не сверен слайсом B),
`too_soon`, `decimals_unknown`, `supply_unreadable` (контракт не ответил на
`totalSupply`), `allocation_over_100`, `allocation_invalid`, `unlock_invalid`,
`too_many_excluded`, `address_invalid`. Сетевые коды переиспользуются из
слайса B: `rpc_unreachable`, `rpc_error`, `decode_failed`.

## Тестирование

Чистыми функциями, без сети и базы:

- `unitsToCoins`: 18 знаков, 0 знаков, uint256 на максимуме, дробный остаток,
  отрицательного входа не бывает (строка без минуса) → ошибка;
- `parseExcluded`: старый список строк, новые строки с подписями, смесь обоих,
  дубликаты адресов в разном регистре, мусор вместо адреса, больше 20 строк,
  всегда добавленные адреса сжигания;
- `computeSupply`: исключения меньше общего, равны ему, больше него (зажим в
  ноль, а не отрицательный оборот), один адрес с ошибкой → `partial = true` и
  его баланс не в сумме;
- `claimedDeltaPct`: заявление совпало, завышено, занижено, не задано (null);
- `marketCap` / `fdv`: `max` задан и не задан, цена null;
- `validateAllocation`: сумма 100, сумма 99.7 (допуск), сумма 100.6 → ошибка,
  отрицательный процент, строка без подписи, 21 строка;
- `validateUnlocks` и `unlockSummary`: окна 30 и 90 дней на границах, разлок
  сегодня, прошедшие события, `pct` против `amount`, сортировка;
- полнота карточки: сумма весов ровно 100 после добавления аллокации и
  разлоков (существующий тест, новые веса).

С подменённым `fetch`: чтение `totalSupply` и балансов (успех, таймаут одного
адреса, `rpc_error` от узла, пустой ответ).

На `PrismaLike`: прогон `syncCardSupply` — карточка без канонического
контракта пропускается, карточка с ним получает запись и провенанс
`VERIFIED_ONCHAIN` на `supply.circulating`; повторный прогон обновляет, а не
дублирует; `syncCardMarkets` пишет `marketCapUsd` с `supplySource = ONCHAIN`
при наличии записи и `SELF_REPORTED` без неё.

## Границы слайса

**Входит:** модель `CoinCardSupply`, чтение балансов исключений, расчёт
циркулирующего выпуска с провенансом, капитализация и FDV в индексе, строки
аллокации и разлоков с валидацией и рендером, редакторы в кабинете, кнопка
ручного пересчёта, воркер-прогон, 10 локалей, тесты.

**Не входит:** чтение контрактов локеров (Unicrypt/Team Finance/Sablier) —
отдельный слайс; сортировка каталога монет по нашей капитализации (каталог
сейчас сортируется по фиду CoinGecko — трогать его в этом слайсе не будем);
график капитализации во времени (история цены есть, история выпуска — нет);
не-EVM сети (Solana, TON) — там нет `balanceOf`, нужен свой слайс;
уведомления о приближающемся разлоке (алерты — отдельная подсистема).
