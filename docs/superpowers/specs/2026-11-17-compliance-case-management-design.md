# Админка как управление делами: плитки очередей, портал переписки, след комплайнса

Дата: 2026-11-17. Слайсы AN–AR.

## Жалоба

Админка — девять закладок с таблицами (`src/components/admin/nav.tsx`), и с телефона
ей пользоваться нельзя: полоса закладок листается вбок, строка таблицы шире экрана,
действие спрятано в подчёркнутое слово. Владелец сидит с телефона и это его основной
доступ.

Хуже формы — то, чего нет вовсе:

1. **Нельзя ответить заявителю.** Человек подал заявку, у него не читается скан — и
   единственный наш ход это «отклонить с причиной». Диалога нет; заявитель не знает,
   что от него хотят, а мы теряем годную заявку.
2. **Не видно, кто проверил и что именно сверил.** `AdminAuditLog` пишет «одобрил
   карточку», но не «сверил юридическое лицо с реестром в 10:24». Решение не
   воспроизводимо: через год никто не ответит, на основании чего пустили.
3. **Одобряет один человек.** Нет второй подписи, нет разделения «проверил» и
   «утвердил».
4. **Нет срока.** Заявка может лежать месяц, и ни одна цифра об этом не скажет.
5. **Нет учёта труда.** Сколько времени сотрудник потратил на дело — неизвестно, и
   значит нечем мерить работу специалистов.
6. **После листинга связь обрывается.** Предприятие залистовано — и всё; ни
   предупреждения, ни пересмотра, ни вопроса «почему точка закрыта».
7. **Нерабочие точки некому вычищать.** Клиент приходит к магазину, там закрыто — и
   он не может нам об этом сказать. Точка остаётся на карте вечно.

## Модель, которую берём

Мировая практика комплайнса (Sumsub, Alloy, Persona, ComplyAdvantage, Wolfsberg CDD)
устроена одинаково и называется **управление делами** (case management). Заявка —
не строка в таблице, а **дело**, у которого есть:

очередь → взятие в работу конкретным сотрудником → часы срока (SLA) → лист проверок
с отметкой по каждому пункту → **запрос дополнительной информации заявителю** (RFI —
request for information, тот самый «портал переписки») → решение по **правилу четырёх
глаз** (проверил один, утвердил второй) → **неизменяемый журнал** всего, что
происходило. После одобрения дело не закрывается: идёт периодический пересмотр,
предупреждения и, при необходимости, приостановка.

**Главное решение по устройству: один слой дела поверх всех типов заявок.** Не
пришиваем переписку, проверки и журнал к каждой из девяти таблиц по отдельности —
пишем один раз и подключаем к монете, предприятию, точке, бирже, финтеху и KYB.
Иначе шесть почти одинаковых реализаций разойдутся в поведении через месяц.

## Данные

Новые модели (Prisma; названия полей — рабочие, точный вид фиксирует план):

```
ComplianceCase
  id, subjectType (COIN_CARD|COMPANY|POINT|EXCHANGE|FINTECH|KYB|COIN_REQUEST|POINT_REPORT)
  subjectId                      // id записи в своей таблице
  status (NEW|IN_REVIEW|WAITING_APPLICANT|READY_FOR_APPROVAL|APPROVED|REJECTED|CLOSED)
  riskLevel (LOW|MEDIUM|HIGH)
  assigneeId?                    // кто взял в работу
  reviewedById?, reviewedAt?     // первая подпись («проверил»)
  approvedById?, approvedAt?     // вторая подпись («утвердил»)
  soleSignOff Boolean            // утверждено одним лицом — второго не было
  decision?, decisionReason?
  applicantUserId                // с кем ведём переписку
  openedAt, dueAt, clockStoppedAt?, slaSeconds   // часы срока
  handledSeconds                 // время в руках, сумма сеансов
  firstResponseAt?, decidedAt?
  @@index([status, dueAt]) @@index([assigneeId, status]) @@unique([subjectType, subjectId])

CaseCheck      caseId, key, state (TODO|OK|FAIL|NA), checkedById?, checkedAt?, note?
CaseDocument   caseId, kind, url, label, verdict (PENDING|ACCEPTED|REJECTED|RESUBMIT),
               verdictById?, verdictAt?, verdictNote?
CaseMessage    caseId, authorId, authorSide (STAFF|APPLICANT), body, attachments Json?,
               readByApplicantAt?, readByStaffAt?, createdAt
CaseEvent      caseId, actorId?, actorSide, kind, payload Json?, createdAt   // неизменяемый
CaseTimeEntry  caseId, userId, startedAt, endedAt?, seconds, source (AUTO|MANUAL), note?
AdminNotification  userId, kind, caseId?, title, body?, readAt?, createdAt
PointReport    pointId, reporterUserId?, reporterIpHash, reason (CLOSED|NO_CRYPTO|
               WRONG_ADDRESS|OTHER), comment?, photoUrl?, createdAt
```

Существующие таблицы (`CoinCard`, `Company`, `CompanyPoint`, …) **не ломаем**: их
`status` остаётся источником правды для публикации, дело лишь ведёт процесс и в конце
проставляет этот статус. Миграция заводит дела для всех уже лежащих заявок со статусом
`PENDING` (бэкфилл), иначе очереди после выкатки окажутся пустыми.

`AdminAuditLog` остаётся как есть — он про то, *что* админ сделал с объектом;
`CaseEvent` про то, *как шла работа по делу*. Смешивать их нельзя: журнал дела должен
быть читаемым рассказом с минутами, а не перечнем enum-кодов.

## Часы: два разных числа

Их обязательно разводить, иначе получится неправда.

**Срок перед заявителем** (`dueAt`, `slaSeconds`) — сколько дело лежит от подачи до
решения. Часы **останавливаются**, когда дело переходит в `WAITING_APPLICANT`, и
снова идут, когда заявитель ответил. Без остановки виноватым оказывается проверяющий,
а молчал заявитель. Срок по умолчанию — 5 рабочих дней, у KYB 10; цветная точка на
плитке: зелёная в сроке, жёлтая осталось меньше четверти, красная просрочено.

**Время в руках** (`handledSeconds`, строки `CaseTimeEntry`) — сколько сотрудник
реально держал дело. Меряется сеансами: открыл дело — пошёл таймер; ушёл со страницы,
закрыл вкладку или 5 минут без единого действия — таймер встал и записал сеанс.

Честная оговорка, которую пишем и в интерфейсе: **это приблизительное измерение**.
Оно меряет время с открытым делом, а не время размышления. Поправить число руками
можно, но только с причиной, и правка ложится в `CaseEvent` отдельной записью —
тихо подправить нельзя, иначе показатель перестанет что-либо значить.

Отсюда аналитика по сотруднику: закрыто дел, среднее время в руках на дело, среднее
время до первого ответа заявителю, доля отказов, сколько просрочено, сколько раз
запрашивал документы повторно.

## Правило четырёх глаз

`reviewedById` ≠ `approvedById` — проверивший не может утвердить сам. Кнопка
«Одобрить» недоступна, пока: лист проверок не закрыт, есть документы в состоянии
`RESUBMIT`, или нет второй подписи. Причина недоступности написана **прямо под
кнопкой**, а не спрятана в подсказку.

Оговорка, без которой правило ломает систему: оно требует двух живых людей. Если
активным сотрудником останется один, одобрение заблокируется навсегда. Поэтому:
есть второй сотрудник — вторая подпись обязательна; он один — решение проходит, но
`soleSignOff = true`, и в журнале это написано словами: «утверждено одним лицом,
второго не было». Молчаливое послабление было бы хуже отсутствия правила.

## Переписка (портал RFI)

Одна нитка на дело. Слева заявитель, справа мы. Вложения прямо в сообщении (те же
корни загрузок, что у логотипов и фото точек — `/var/www/trientes-uploads`, см.
CLAUDE.md: класть в `public/` нельзя, Next запекает его в сборку).

- Сотрудник пишет из дела; заявитель — из своего кабинета (`/cabinet` или
  `/business`, раздел «Переписка по заявке»).
- Заготовки в одно нажатие: запросить документ, уточнить данные, нужен перевод,
  срок ответа 7 дней.
- Отправка сообщения заявителю переводит дело в `WAITING_APPLICANT` и **останавливает
  часы срока**; ответ заявителя возвращает в `IN_REVIEW` и запускает их снова.
- Заявителю уходит `notifyUser` (Telegram → email → web-push) — тот же канал, что у
  приглашений в команду.
- Непрочитанные сообщения считаются по стороне и показываются колокольчиком на плитке
  очереди и на самом деле.

## Уведомления внутри админки

`AdminNotification` + колокольчик с числом в шапке админки. Поводы: назначили на тебя
дело, попросили вторую подпись, заявитель ответил по твоему делу, срок подходит
(за сутки), пришла жалоба на точку, дело просрочено. Дубль в Telegram, если у
сотрудника привязан (тот же `notifyUser`).

## Жалобы на точки

В карточке точки навигатора — кнопка «Сообщить о проблеме»: закрыто / не принимает
крипту / адрес неверный / другое, плюс текст и фото по желанию.

Защита от баловства обязательна: **точку нельзя снимать с карты по одной жалобе** —
иначе конкурент закроет любой магазин одним нажатием.

- Не чаще одной жалобы в сутки с одного адреса на одну точку (`reporterIpHash`,
  как в `LoginAttempt`).
- Все жалобы на точку собираются **в одно дело** (`subjectType = POINT_REPORT`),
  а не плодят десять.
- Три независимые жалобы за 60 дней → точка получает пометку «проверяется» (видна в
  навигаторе, но не снята), дело поднимается в приоритете, предприятию уходит вопрос
  через ту же переписку.
- Нет ответа за 14 дней → предупреждение владельцу; ещё 14 дней молчания → точка
  снимается с карты до выяснения, с записью причины.

## Панель залистованного предприятия

Отдельный экран управления уже одобренным предприятием: три числа сверху (точки,
карточки, команда), раздел надзора (последняя проверка и кто одобрил, состояние KYB,
активные предупреждения, срок следующего пересмотра), раздел связи (написать /
вынести предупреждение — уходит в кабинет и в Telegram с почтой владельцам), раздел
объектов (точки, карточки, команда) и статус листинга (приостановить / снять, причина
обязательна и уходит предприятию). Приостановка скрывает точки и карточки с сайта,
но сохраняет дело и переписку.

Периодический пересмотр: у одобренного дела ставится `nextReviewAt` (по умолчанию
12 месяцев, у высокого риска 6). Воркер за 30 дней до срока заводит дело пересмотра и
звонит колокольчиком.

## Правила вида (на всю админку)

- **Никаких ссылок-слов в качестве действия.** Любое действие — кнопка высотой не
  меньше 44 px, на телефоне во всю ширину колонки.
- **Всё по центру.** Контент — колонка по центру экрана; на компьютере та же колонка
  шире (max-width ~1100 px) и плитки идут в 3–4 ряда вместо двух. Один набор
  компонентов на оба размера, а не два экрана.
- Плитка очереди — квадрат (`aspect-square`) со скруглением 22 px: крупное число дел,
  подпись, возраст старейшей заявки, цветная точка срока, оранжевый колокольчик с
  числом непрочитанных сообщений. Пустая очередь — серым, без крика.
- Дело раскрывается разделами, каждый одной строкой говорит своё состояние
  («3 из 4 приняты», «5 из 7»), и только нужный раздел раскрыт.
- Макеты, утверждённые владельцем 17 ноября: `trientes-artifacts/mockups/*.html`,
  снимки — `trientes-artifacts/screens/admin-{1..4}-*.png`.

## Разделение на слайсы

Каждый кусок сам по себе уже польза; порядок обязателен — следующий опирается на
предыдущий.

1. **AN — основа.** Модели `ComplianceCase` / `CaseEvent` / `CaseTimeEntry`, бэкфилл
   дел для лежащих заявок, экран плиток очередей, раскрытие дела (анкета, документы,
   журнал), взятие в работу, сроки с остановкой часов, учёт времени сеансами.
   Старые экраны очередей остаются рабочими до конца слайса 3.
2. **AO — переписка и колокольчики.** `CaseMessage`, нитка в деле, раздел в кабинете
   заявителя, заготовки, `AdminNotification` + колокольчик в шапке, дубль в Telegram.
3. **AP — проверки, подписи, аналитика.** `CaseCheck` с листами под каждый тип заявки,
   `CaseDocument` с вердиктами, правило четырёх глаз, замена старых экранов очередей
   на дела, аналитика по сотрудникам.
4. **AQ — жалобы на точки.** Кнопка в навигаторе, `PointReport`, очередь саппорта,
   пороги и эскалация.
5. **AR — надзор над залистованным предприятием.** Панель управления, предупреждения,
   приостановка, периодический пересмотр в воркере.

## Чего сознательно не делаем

- **Автоматической проверки по санкционным спискам.** Пункт в листе есть, человек его
  закрывает руками. Подключение платного провайдера (ComplyAdvantage, Refinitiv) —
  отдельное решение владельца, а не часть этой работы.
- **Расчёта риска формулой.** `riskLevel` ставит человек; автоматический скоринг без
  данных об отказах будет выдумкой.
- **Отдельных ролей комплайнса на первом слайсе.** Пока доступ по `ADMIN`, как
  сейчас; роли (COMPLIANCE / SUPPORT / ADMIN) вводятся в слайсе AP, когда появится
  что разделять.
- **Переписки с анонимом.** Жалобу на точку может оставить кто угодно, но вести
  диалог мы будем только с зарегистрированным заявителем.
- **Шифрования переписки.** Она лежит в базе как есть; KYB-документы по-прежнему вне
  публичных корней загрузок.
