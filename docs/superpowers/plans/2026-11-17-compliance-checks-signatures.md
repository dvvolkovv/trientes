# Слайс AP — проверки, подписи, аналитика: план работ

**Спека:** `docs/superpowers/specs/2026-11-17-compliance-case-management-design.md`
(разделы «Правило четырёх глаз», «Данные», «Часы: два разных числа»).

**Goal:** дать делу лист проверок и вердикты по документам, развести «проверил» и
«утвердил» двумя подписями, увести решение по заявке из старых таблиц в дело (одна
дверь к решению) и показать труд сотрудников числами.

**Architecture:** как в AN/AO — вся арифметика чистыми функциями в `src/lib/cases/*`
с юнит-тестами, запись в базу тонкими серверными экшенами, экраны серверные.

---

## Решения, принятые до кода

1. **Лист проверок живёт в коде, состояние — в базе.** `CaseCheck` заводится строкой
   только когда сотрудник отметил пункт; сам список — `src/lib/cases/checklists.ts`.
   Если заводить строки при открытии дела, список замрёт на том виде, в каком был в
   день подачи, и новый пункт не появится у трёхсот уже открытых дел.
2. **Одобрение не блокируется пунктом в состоянии FAIL.** Блокирует только `TODO` у
   обязательного пункта: решение требует, чтобы по каждому пункту был дан *ответ*, а
   не чтобы все ответы были «да». Иначе проверяющий, которому надо пустить заявку с
   одним честным «нет», переправит FAIL в NA, и показатель начнёт врать.
3. **FAIL и NA требуют примечания (≥3 символа), OK — нет.** Через год «не применимо»
   без причины не значит ничего. Порог тот же, что у причины отказа.
4. **Отказ второй подписи не требует.** Он ничего не публикует, а заявитель может
   подать заново; требование двух глаз на отказ оставило бы годную заявку висеть,
   пока второй сотрудник не придёт. Причина отказа обязательна.
5. **Документы не загружаются в деле заново.** `CaseDocument` собирается из двух уже
   существующих источников — `Company.kybDocuments` и вложения сообщений заявителя;
   вердикт ставится на то, что человек прислал. Третьего пути загрузки не заводим, и
   приватный корень из AO остаётся единственным местом файлов переписки.
6. **Строка документа не удаляется, даже если документ исчез из источника.** Его
   видели и по нему высказались; снос строки стёр бы вердикт.
7. **Решение сначала применяется к объекту, и только потом пишется в дело.** Если
   объект уже решён вне дела (`not_pending` — такое возможно у 33 дел посева),
   дело закрывается как `CLOSED` с записью в журнал, а не остаётся в очереди навсегда.
8. **Старые экраны перестают показывать ожидающие заявки.** Решение, принятое там,
   прошло бы мимо листа проверок и мимо второй подписи — две двери к одному решению
   означают, что правило четырёх глаз не действует. Всё, что не является очередью
   (владение карточками, правки, удалённые записи, курируемый финтех), на этих
   экранах остаётся.
9. **Ролей комплайнса в этом слайсе по-прежнему нет.** Правило четырёх глаз различает
   людей, а не роли; разделять пока нечего, а роль, выданная не тому из двух админов,
   заблокировала бы одобрение вообще. Вводить вместе с третьим сотрудником.
10. **Труд считается на того, кто вёл дело** (`reviewedById ?? assigneeId`), вторая
    подпись считается отдельным числом. Иначе утвердивший чужое дело за минуту
    выглядел бы в таблице как закрывший его.

## Карта файлов

Создаём:

| Файл | Ответственность |
|---|---|
| `src/lib/cases/checklists.ts` | Списки пунктов по типу заявки, обязательность, подсчёт |
| `src/lib/cases/approval.ts` | Правило четырёх глаз: препятствия, подпись одним лицом |
| `src/lib/cases/documents.ts` | Сбор документов дела из источников, дедупликация |
| `src/lib/cases/decide.ts` | Применение решения к объекту заявки по типу |
| `src/lib/cases/staff-stats.ts` | Аналитика по сотрудникам (чистая арифметика) |
| `src/app/actions/case-review.ts` | Экшены: пункт, вердикт документа, подписи, решение |
| `src/components/admin/case-checklist.tsx` | Пункты листа с кнопками OK/FAIL/NA |
| `src/components/admin/case-documents.tsx` | Документы с вердиктами |
| `src/components/admin/case-decision.tsx` | Две подписи, причина недоступности под кнопкой |
| `src/app/[locale]/admin/staff/page.tsx` | Таблица труда сотрудников |
| `tests/case-checklists.test.ts`, `tests/case-approval.test.ts`, `tests/case-documents.test.ts`, `tests/case-staff-stats.test.ts` | Границы |

Правим: `prisma/schema.prisma` + миграция `20261117210000_case_checks_signatures`,
`src/lib/cases/journal.ts` (новые виды событий), `src/app/[locale]/admin/cases/[id]/page.tsx`
(разделы 3–5, журнал уезжает в конец), `src/components/admin/nav.tsx` (закладки),
старые экраны очередей, `messages/en.json` + `npm run i18n`.

- [ ] 1. Схема: поля подписей и решения в `ComplianceCase`, модели `CaseCheck` и
      `CaseDocument`, перечисления `CaseCheckState`/`CaseDocumentVerdict`/`CaseDecision`,
      виды событий `REVIEWED`/`CHECK_SET`/`DOCUMENT_VERDICT`. Миграция руками +
      `migrate deploy` (чекаут — прод, `migrate dev` умеет предлагать сброс базы).
- [ ] 2. `checklists.ts` + тест: у каждого типа заявки непустой список, у каждого
      пункта есть ключ перевода, подсчёт «закрыто из обязательных».
- [ ] 3. `approval.ts` + тест: препятствия (`checks_pending`, `documents_resubmit`,
      `not_reviewed`, `same_person`), подпись одним лицом при единственном сотруднике.
- [ ] 4. `documents.ts` + тест: сбор из `kybDocuments` и вложений заявителя,
      дедупликация по адресу, идемпотентный `syncCaseDocuments`.
- [ ] 5. `decide.ts`: применение решения по типу заявки через существующие экшены,
      обработка `not_pending` → `CLOSED`.
- [ ] 6. Экшены `case-review.ts`: `setCaseCheck`, `setDocumentVerdict`, `markReviewed`,
      `decideCase`. Каждый пишет событие журнала.
- [ ] 7. Экраны дела: разделы «Проверки», «Документы», «Решение»; причина
      недоступности кнопки — строкой под кнопкой, как велит спека.
- [ ] 8. Старые экраны: убрать списки ожидающих, оставить остальное; закладка
      «Сотрудники» в полосе админки.
- [ ] 9. `staff-stats.ts` + тест и экран `/admin/staff`.
- [ ] 10. `messages/en.json`, `npm run i18n`, `npx vitest run`, `npm run build`,
      `pm2 restart trientes-web trientes-worker`, живой прогон, коммит и push.
